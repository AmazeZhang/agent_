# 项目二 Agentic RL 失效诊断与修复建议

- 编写日期：2026-08-08
- 适用项目：`project2-coding-agent-rl`
- 诊断基线：GitHub 仓库 `AmazeZhang/agent_` 的 `main` 分支，最新检查提交为 `cbeab681e9f25c9710848ee5284e0c2af0c8da40`
- 文档性质：阶段性诊断与后续实施草案，可继续补充实验记录、资源预算和最终结果

## 1. 执行摘要

项目二已经打通了以下工程链路：

```text
任务与轨迹数据
  → SFT
  → GRPO
  → checkpoint
  → PEFT/LoRA 导出
  → vLLM 服务
  → SWE-agent 留出评测
```

但“工程链路能够运行”不等于“Agentic RL 已经有效”。现有实验的核心结果是：

- SWE-smith Pilot 得到 20 条可信 rollout，其中 15 条 reward 1、5 条 reward 0；
- SFT 完成了真实参数更新；
- 四次 GRPO 的 reward 全部为 0；
- GRPO 日志中 `actor/pg_loss=0`、`grad_norm=0`；
- GRPO LoRA 的 `lora_B` 保持全零，说明策略实际上没有获得有效更新；
- WP7 的 base、SFT、GRPO 三组模型在 5 个留出任务上共 15 次运行，全部未调用 `submit`，最终为 0/15。

因此，项目二当前更准确的结论应为：

> 项目已经验证了 Coding Agent 数据、训练、checkpoint、推理服务和评测之间的工程连接性，但尚未验证出有效的 Agentic RL 学习效果。当前结果可以作为一个具有明确根因证据的负实验基线。

## 2. 主要问题诊断

### 2.1 GRPO 环境不是真正的 Coding Agent 环境

当前 `SweSingleTurnWorkflow` 只向模型提供问题描述，然后要求模型一次性生成 unified diff。

模型无法在生成补丁前执行以下关键行为：

- 查看仓库文件；
- 搜索符号和调用关系；
- 运行失败测试；
- 根据错误输出修改实现；
- 多轮验证候选补丁；
- 最后调用 `submit`。

这会导致模型只能根据 issue 猜测文件路径、函数位置和 diff hunk 行号。对 3B 模型而言，生成不可应用或内容虚构的补丁是预期结果，而不是偶发异常。

真正的 Coding Agent RL 环境应当是：

```text
Issue + Repository
  → search/read/bash
  → observation
  → edit
  → test
  → observation
  → revise
  → submit
  → isolated hidden-test evaluation
  → reward
```

### 2.2 SFT、GRPO 和评测协议不一致

当前至少存在三套协议：

| 阶段 | 模型学习或使用的格式 |
|---|---|
| SFT#1 | SWE-agent 工具调用轨迹：`bash`、`str_replace_editor`、`submit` |
| SFT#2 / GRPO | 单轮输出完整 unified diff |
| WP7 | SWE-agent `thought_action` 多轮文本协议 |

协议错位带来两个直接问题：

1. SFT#1 学到的工具调用无法被只接受独立 diff 的 GRPO reward 消费；
2. SFT#2 和 GRPO 学习的是 direct-diff 任务，但 WP7 却用多轮 Agent 协议评测，因此 WP7 没有在训练协议下直接测量模型能力。

后续必须让 SFT、RL rollout 和 holdout evaluation 使用完全相同的：

- system prompt；
- chat template；
- 工具名称与参数 schema；
- observation 编码；
- 上下文裁剪方式；
- `submit` 语义；
- 最大步骤数与 token 预算。

### 2.3 数据量不足

现有 SFT#2 约 14 条金补丁、1 epoch。该规模可以验证训练代码和权重写入，但不足以让 3B 模型学习复杂的软件工程修复能力。

尤其是金补丁 direct-diff 数据只告诉模型最终答案，没有提供：

- 如何定位相关文件；
- 为什么选择某个修改点；
- 测试失败如何引导修复；
- 修改后如何验证；
- 错误尝试如何恢复。

建议第一阶段至少准备：

- 200–500 个训练任务；
- 每个任务 4–8 条 rollout；
- 数百条独立验证成功的完整多轮轨迹用于 SFT；
- 同时保留成功、失败和部分改进轨迹；
- 训练集、开发集和留出集按任务严格隔离。

### 2.4 GRPO 没有获得组内 reward 方差

GRPO 依赖同一任务的一组 rollout 之间存在 reward 差异。如果每组 rollout 都是全 0 或全 1，组内 advantage 为 0，策略不会产生有效更新。

当前四次 GRPO 全零，因此 `pg_loss=0`、`grad_norm=0` 是算法机制下的自然结果。

RL 任务应优先从以下难度区间选择：

- 基座或 SFT 模型偶尔能成功；
- 同一问题多次采样会同时出现成功与失败；
- 经验成功率大约处于 10%–70%；
- 环境和测试足够稳定，reward 可以重复复验。

过难任务会产生全零奖励；过易任务会产生全一奖励，两者都不适合直接用于 GRPO。

### 2.5 Reward 实现仍需加固

当前 reward 的设计意图是：

```text
0.0  补丁无法应用
0.3  补丁可应用但测试失败
0.5  测试套件干净
1.0  FAIL_TO_PASS 全通过
```

但现有实现中，如果测试套件没有失败，`0.5` 会立即被后续条件覆盖为 `1.0`，因此 `0.5` 基本不可达。此外还需要防范以下情况：

- pytest 收集到 0 个测试却被判成功；
- `FAIL_TO_PASS` 测试名称没有匹配到 JUnit 条目；
- 测试进程异常退出但生成了不完整 XML；
- 模型修改测试文件；
- 模型删除或跳过测试；
- 补丁修改超出任务允许范围；
- 环境故障被误记为模型 reward 0。

建议将 reward 明确拆为可审计字段：

```json
{
  "valid_action": true,
  "patch_applied": true,
  "tests_collected": 673,
  "fail_to_pass_matched": 4,
  "fail_to_pass_passed": 4,
  "pass_to_pass_passed": 669,
  "tests_modified": false,
  "eval_infra_error": false,
  "final_reward": 1.0
}
```

## 3. 修复目标架构

### 3.1 统一多轮 Agent Harness

建议优先使用 Mini-SWE-Agent 风格的简单文本协议，或者使用经过端到端验证的原生 function-calling 协议。

最少提供以下工具：

| 工具 | 作用 |
|---|---|
| `bash` | 执行受限 shell 命令和测试 |
| `read_file` | 读取文件内容和指定行 |
| `search` | 搜索文件、符号和文本 |
| `edit_file` | 修改源代码 |
| `run_tests` | 运行目标测试或完整测试 |
| `submit` | 固化最终 patch 并结束 episode |

每次工具执行结果必须作为 observation 返回给模型。训练 token 应记录模型真实看到的上下文，并为环境 observation 设置正确的 loss mask。

### 3.2 建议的 reward 结构

最终隐藏测试仍应是主要奖励，同时可加入有限的过程塑形，避免训练初期恒零：

| 条件 | 建议 reward |
|---|---:|
| 非法输出、无法解析工具调用 | 0.00 |
| 合法调用并成功执行仓库命令 | 0.02–0.05 |
| 产生非空、可应用且未修改测试的补丁 | 0.15–0.25 |
| 相比基线减少失败测试 | 0.30–0.50 |
| 所有 `FAIL_TO_PASS` 通过 | 0.70–0.85 |
| `FAIL_TO_PASS` 与 `PASS_TO_PASS` 全部通过 | 1.00 |

注意：过程奖励不能仅奖励“多调用工具”或“修改代码”，否则模型可能学会延长轨迹或制造无意义修改。

### 3.3 RL 启动前门禁

在启动正式 GRPO 前，必须全部满足：

- [ ] gold patch 在 reward evaluator 中稳定得到 1.0；
- [ ] 空补丁、随机补丁和修改测试的补丁稳定得到 0；
- [ ] 收集到 0 个测试时得到 0，并记录为评测异常；
- [ ] SFT 模型合法工具调用率不低于 95%；
- [ ] SFT 模型在部分任务中能够调用 `submit`；
- [ ] SFT 模型在未参与训练的开发集上具有非零 resolve rate；
- [ ] 同一任务的多个 rollout 存在 reward 方差；
- [ ] 轨迹记录包含 prompt token、completion token、loss mask、工具 observation 和最终 reward；
- [ ] SFT、RL 和评测使用同一协议；
- [ ] holdout 任务未进入 SFT、RL 选样、提示调试或超参数选择。

如果这些门禁未通过，继续增加 GRPO run 数量通常不会产生有效收益。

## 4. 推荐开源方案

### 4.1 Uni-Agent：首选迁移目标

- 仓库：[verl-project/uni-agent](https://github.com/verl-project/uni-agent)
- 定位：长程 Agent 推理、数据采集和 RL 训练框架；
- 优点：可以接入 Mini-SWE-Agent 等现有 harness；训练与推理复用相同交互栈；支持沙箱、工具、任务和 reward 解耦；
- 与本项目的匹配度：最高；
- 建议用途：用它替换当前单轮 `SweSingleTurnWorkflow`，保留现有 SWE-smith 数据与评测容器。

截至本报告编写时，该项目公开展示了 Coding Agent RL 结果，包括在 SWE-reBench 上使用 9B 模型进行 GRPO，并报告了训练前后的提升。实际复现仍需以仓库当前 recipe、依赖版本和硬件说明为准。

### 4.2 SWE-Master：最完整的 Coding Agent 参考实现

- 仓库：[RUCAIBox/SWE-Master](https://github.com/RUCAIBox/SWE-Master)
- 定位：面向软件工程 Agent 的完整 post-training pipeline；
- 覆盖：轨迹合成与清洗、长程 SFT、执行反馈 RLVR、测试时扩展、LSP 工具；
- 已发布模型：4B-SFT、4B-RL、32B-SFT、32B-RL、32B-RL-LSP；
- 建议用途：先使用 4B-RL 模型验证本项目的 harness 和评测链路，再参考其数据筛选与训练实现。

这是当前最适合用来回答“一个经过 Agentic SFT/RL 的小模型是否能在当前评测环境中正常提交补丁”的现成对照组。

### 4.3 OpenClaw-RL / SWE-RL：透明但资源要求较高

- 仓库：[Gen-Verse/OpenClaw-RL/swe-rl](https://github.com/Gen-Verse/OpenClaw-RL/tree/main/swe-rl)
- 定位：基于 slime 的 SWE-bench/SWE-Gym 多轮 RL；
- 交互方式：模型在隔离 Docker 容器中生成 bash 命令、接收执行结果、提交 patch，再由新容器运行官方测试；
- 优点：数据流、远程容器、轨迹编码、loss mask、reward 和评测路径比较完整；
- 限制：官方轻量 8B 配置仍使用 2 节点、16 GPU，不能直接按原配置在当前机器上运行。

建议借鉴其多轮环境和 token/loss-mask 实现，不建议直接照搬其大规模训练配置。

### 4.4 verl-agent / 原生 verl

- 仓库：[langfengQ/verl-agent](https://github.com/langfengq/verl-agent)
- 原生框架：[verl-project/verl](https://github.com/verl-project/verl)
- 能力：多轮 Agent-Environment 交互、step-wise rollout、工具调用、LoRA、GRPO/GiGPO/PPO 等；
