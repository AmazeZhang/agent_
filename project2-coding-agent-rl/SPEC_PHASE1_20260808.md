### 3.2 过滤链路（复用 SWE-Master 官方脚本，按序）

1. **resolved 标签过滤**：trajectories 只留 `resolved=True`（正例）与 `resolved=False`
   且 `model` 为 claude-3-7-sonnet 的轨迹（负例备用）——首筛
2. **bon pass-rate 过滤**（`bon_filter/` 三步）：按 instance 聚合 pass rate，
   剔除 trivial（≈1.0）与 intractable（≈0）两极，保留 0.2-0.8 中间带
3. **任务与 phase0 兼容性检查**：任务 repo 需满足——纯 Python、轻依赖（pip 可装）、
   无重型 C 扩展；与现有 5 任务同风格（boltons/funcy/pygments/stackprinter 级）
4. **规则评估器复核（G1）**：任务自带的 patch 用我们 phase0 评估器验证。
   ⚠️ **SWE-smith 语义与 SWE-bench 相反**：数据集里的 patch 是*引入 bug* 的
   （broken 状态 = commit + apply patch；agent 的修复 = patch 的反向）。
   复核三条件（已实测 cloudpickle 任务通过）：
   - clean 状态（commit 原样）f2p 全过 → 修复可达、测试有效
   - apply patch 后（broken）f2p 有失败 → bug 真实
   - p2p broken vs clean delta=0 → 不破坏既有行为
5. **上下文适配筛选**：轨迹总长 ≤32K token（7B/24GB 训练上限），保证 RL 阶段可用

输出统计：各步丢弃数量/原因 → `stats/filter_report.jsonl`。

### 3.5 任务环境语义（重要修正，2026-08-08 实测确认）

**SWE-smith patch 方向与 SWE-bench 相反**（来自数据集实测 + 论文/适配器验证）：
- 数据集 `patch` 字段 = **引入 bug 的 diff**（不是修复）
- agent 的**初始代码状态** = checkout commit + `git apply <bug patch>`（broken）
- 模型修复的正确解 = `git apply -R <bug patch>`（反向变换）
- 判定：修复后 f2p 全过 + p2p delta=0（相对 clean 基线）

**环境构建流程**（gold_review.py 已验证）：
1. git worktree @ task commit（blob:none 共享对象库）
2. 任务 venv + `pip install -e .`（失败则 PYTHONPATH fallback）+ pytest
3. 测试依赖自动补装（解析 ModuleNotFoundError，最多 4 轮重试）
4. 三条件复核：clean f2p 全过 ∧ broken f2p 有失败 ∧ p2p delta=0

**数据质量审计发现**：
- `swe-smith-trajectories` 的 **patch 列存在系统性错位**（pool 内 220/311=71% 的
  resolved 轨迹 patch 属于其他 repo，呈循环移位模式）；**messages 列与 instance
  匹配**（抽查 cloudpickle/PySnooper 均正确）→ SFT 管道只用 messages，不受影响；
  gold patch 一律从 tasks parquet 取（已实测 apply 成功、语义正确）
- 结论：trajectories 只作对话数据源；任务有效性判定只依赖 tasks parquet + 测试
